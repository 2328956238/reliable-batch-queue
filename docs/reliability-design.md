# 可靠性设计与说明

这份说明对应 2026-10-14 脱敏展示版增强。新增重试治理能力没有部署到生产，不应用“线上已承载”“降低故障率”等未测量表述。

## 1. 为什么把重试预算写进任务记录

如果预算只在 Worker 配置里，重启、切换进程或上线新默认值会悄悄改变既有任务的处理上限。这里将 `max_attempts`、基础延迟和封顶延迟随首次入队持久化。实例默认值只决定新任务策略；相同 ID 再次入队不会重置。

每次领取先把历史次数和周期次数都加一，再交给 Worker。失败或者租约回收只判断当前周期次数，没有二次计数。同一个 Claim 只可能被释放一次，下一次提交会因所有权不匹配而被拒绝。

人工重放是一项独立、可追踪的决策：它只允许死信任务回到 ready，要求操作者和原因，恢复一个完整周期的原预算。历史次数始终递增。库没有账户系统，`actor` 是调用方提供的审计标签，不是已经验证的身份。

## 2. 为什么租约过期也计入预算

只限制 `fail()` 会漏掉进程反复崩溃、OOM 或机器断电。领取已经消耗一次尝试，过期回收时判断相同预算，因此持续超时也会进入死信。默认回收后先退避，避免立即重复启动必然失败的任务。

代价是恢复速度：瞬时进程中断也需要等待退避。重试策略可以设为零延迟，但默认优先控制重复压力。此示例没有随机抖动；大规模同时间失败时，指数退避本身不能解决惊群。

## 3. 为什么审计和状态使用同一事务

先提交状态再写日志会产生“已死信但无原因”的空档，先写日志再提交状态则可能记录并未发生的迁移。每次成功状态修改和事件插入放在同一 `BEGIN IMMEDIATE` 事务，日志失败时状态一起回滚。

故障注入使用 SQLite `BEFORE INSERT` trigger 主动拒绝审计写入，验证状态仍保持旧值；这比仅断言正常日志内容更能说明事务边界。它模拟数据库写入失败路径，并不等同于真实断电或文件系统损坏测试。

事件通过全局递增 ID 游标分页；按同一数据库已提交顺序读取，而不是按墙上时钟排序。系统时间回拨也不会改变事件游标顺序。日志消费者自行保存游标与处理幂等性，库不提供日志投递 exactly-once。

## 4. 为什么保留 Claim/Session fencing

最大重试次数只能限制执行次数，不能识别谁有权提交。新 Worker 领取后，旧 Worker 可能从暂停中恢复；如果只根据任务 ID 更新，它仍可错误地把新任务标记成功。所有写入都需要 Worker、Claim、Session 完全匹配。

会话轮换在写事务内做比较交换。重放后的新领取生成不同 Claim ID，因此旧 Claim 即使携带相同 Worker ID 也不能改写新周期。

队列 fencing 与业务幂等是两个层次：这里的校验保护队列状态，不能阻止旧进程已经向外部支付、邮件或库存系统产生副作用。外部调用必须另做幂等键、业务事务或支持 fencing token 的资源端校验。

## 5. 为什么选 SQLite，何时应该换

单机队列的目标是用少量依赖清楚表达事务边界；SQLite 的串行写锁让选择、领取和审计易于原子化，多进程测试验证跨进程锁而非仅 Python 锁。

取舍是所有写操作竞争同一个数据库写锁，心跳审计与批量过期回收会延长等待。当前没有吞吐压测、远端协议、租约分区、高可用或分布式共识；不能声称是 Kafka/Celery 的等价替代品。出现明显写锁瓶颈、跨主机高可用需求时，应选择服务端数据库和协调服务，或成熟消息系统，并重新验证一致性边界。

## 6. 兼容迁移为什么需要重建表

旧表 CHECK 约束不接受 `dead_letter`，SQLite 不能直接更改该列约束。升级时在单事务内重建表并复制原 rowid，避免相同创建时间的任务改变 FIFO 顺序。所有权字段和下一次到期时间原样保留。

旧版没有上限，已有 attempts 可能超过新默认值；迁移时采用 `max(默认值, 历史次数 + 1)`，明确给旧任务至少一次剩余领取机会。不会编造缺失的尝试明细，而是记录基线事件。该折中仅用于一次迁移，之后策略保持持久化。

## 可用于作品集的准确表述

> 实现面向批处理与 ETL 的可靠任务队列，使用 SQLite 写事务完成原子领取、租约恢复与 Claim/Session fencing；在脱敏展示版中扩展持久化重试预算、封顶指数退避、死信重放和同事务审计，并通过独立进程竞争及审计写入故障注入验证恢复与一致性边界。

如果用于公司项目经历，应把既有项目实践与个人展示版增强分开写，不能把这次新增能力直接写为已经上线的公司成果。
